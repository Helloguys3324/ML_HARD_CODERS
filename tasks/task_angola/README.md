## 1. 📖 О чем задача
В Луанде (столице Анголы) цифровой ассистент водоканала отвечает жителям района Киламба на вопрос: *«Дали ли воду в 4-м секторе?»*.

Ассистент выдал жителям ложный ответ: сообщил, что авария продолжается и воды нет, хотя служба водоканала к этому моменту уже всё починила. Нам предоставлен файл телеметрии `test-input.json` с 20 событиями логов вызовов LLM (промпты, вызовы инструментов, память, ответы модели, тайминги).

**Цель:** Найти точный идентификатор элемента в логах, из-за которого модель ошиблась. Этот ID сам по себе и является флагом в формате `SIGMOID_<PHRASE>`.

---

## 2. 🔍 Расследование: в чём была причина лжи?

В логах записано 20 последовательных событий, сгруппированных по трём сессиям одного и того же запроса:

1. **`control-01` (в 13:55) — контрольный запуск без сбоя:**
   - Ассистент вызывает инструмент `get_service_status` $\to$ получает статус `RESTORED` $\to$ честно отвечает: *«Да, воду дали в 13:52»*.
2. **`incident-01` (в 14:05) — тот самый аварийный запуск:**
   - Ассистент снова вызывает инструмент `get_service_status` и снова получает актуальный статус `RESTORED` (вода есть!).
   - **НО** перед генерацией ответа ассистент выполняет поиск по долгосрочной RAG-памяти (`memory.search`).
   - Поиск достаёт из кэша старую утреннюю заметку:
     ```json
     {
       "source_id": "SIGMOID_MEM_KILAMBA",
       "created_at": "2026-10-26T10:00:00+02:00",
       "valid_until": "2026-10-26T10:00:00+02:00"
     }
     ```
   - Заметка внедряется в контекст LLM (`injected_into_context: true`), несмотря на то, что её срок действия (`valid_until`) **истёк 4 часа назад**!
   - Модель верит «воспоминанию» из памяти больше, чем свежему ответу инструмента, и врёт жителям: *«Нет, отключение продолжается»*.
3. **`replay-no-memory` — контрольная проверка инженеров:**
   - Инженеры перезапускают тот же запрос с `memory_enabled: False` $\to$ модель игнорирует кэш и снова отвечает правильно: *«Да, воду дали в 13:58»*.

## 3. ⚙️ Как работает решение (подтверждение строчками кода)

Скрипт `solve.py` автоматически парсит JSON-трейсы событий и изолирует идентификатор сбойной записи памяти:

```python
# Из solve.py: анализ трейсов и извлечение виновного ID памяти
for ev in data["events"]:
    # Событие memory.search в аварийном запуске вернуло протухшую запись:
    if ev.get("event") == "memory.search" and "SIGMOID_" in str(ev.get("result_ids")):
        for rid in ev.get("result_ids", []):
            if rid.startswith("SIGMOID_"):
                flag = rid  # SIGMOID_MEM_KILAMBA
                break
```
